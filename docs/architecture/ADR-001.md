## Contexto e escolha recomendada

I0 comprova cadastro/listagem com persistência real, sem antecipar autenticação, catálogo por personal ou prescrição (D47–48). Recomenda-se um repositório com dois aplicativos, uma API em um único projeto .NET organizada por funcionalidade e PostgreSQL local. Não criar projetos separados de domínio, aplicação e infraestrutura neste recorte.

Estrutura planejada e posteriormente implementada sob D74:

```text
apps/web/                         Next.js App Router, TypeScript, npm e lockfile
apps/api/DeltaFit.Api/             host ASP.NET Core, configuração e erros HTTP
  Features/Exercises/             endpoints, DTOs e validação do cadastro
  Persistence/                    DbContext, mapeamento e migrations
tests/DeltaFit.Api.IntegrationTests/  xUnit, WebApplicationFactory e PostgreSQL
tests/e2e/                        Playwright/TypeScript, Chromium inicialmente
docs/architecture/                ADRs
docs/delivery/                    fichas e evidências
```

Uma solution .NET na raiz reúne API e integração. O runner Playwright e suas dependências podem ficar no pacote web, apontando para tests/e2e; sem monorepo manager ou pacote compartilhado prematuro. Testes unitários ganham projeto próprio somente se surgir regra que justifique isso. Git acompanha a primeira implementação; verificar o repositório existente, preservar seu histórico e não recriá-lo. Não definir remoto, branch policy ou pipeline agora.

### Responsabilidades e transporte

- Página `/exercises`: formulário, lista e estados de interface; cliente HTTP pequeno com endereço da API configurável. API C# é dona da validação definitiva e do acesso ao banco. Navegador nunca recebe conexão PostgreSQL.
- Recomendação: navegador chama diretamente a API local. CORS libera apenas a origem local configurada do frontend; ambos os processos escutam em loopback. Não criar API paralela em Route Handlers/Server Actions nem regras de negócio em Next.js.
- Alternativa: proxy de mesma origem em Next.js simplifica CORS e pode ajudar cookies futuros, mas acrescenta configuração e uma etapa de diagnóstico. Rever quando identidade e hospedagem forem discutidas. CORS não substitui autenticação.
- Estrutura confirmada pelo fundador (D71): Vertical Slice enxuta em um único projeto de API, com Minimal APIs. Em `Features/Exercises/`, `CreateExercise.cs` e `ListExercises.cs` reúnem, por operação, endpoint, entrada, validação e execução. EF Core é usado diretamente nas operações, com DbContext por requisição; DbContext e migrations ficam compartilhados em `Persistence/`. Não adicionar MediatR, repository genérico ou projetos por camada no I0. Controllers foram considerados como alternativa de convenções familiares, sem necessidade concreta neste recorte. Benefício: fluxo localizável e poucas camadas; custo aceito: acoplamento explícito das operações ao EF Core. Organização de comandos/consultas não exige infraestrutura de CQRS, barramento ou microsserviços.
- Respostas não expõem entidades EF diretamente. Contrato HTTP documentado na ficha; geração de cliente e plataforma de versionamento da API ficam para necessidade real.

### Persistência e migrações

- Escolha confirmada pelo fundador (D70): EF Core com provider Npgsql e migrações versionadas. A recomendação anterior foi aceita após comparação com SQL manual. Ganho: mapeamento e migrações no mesmo fluxo .NET. Custo: dependência do ORM e aprendizado de seus comportamentos. Dapper/SQL manual dá controle explícito, mas exige separar migrações e mapeamento sem benefício demonstrado neste recorte.
- EF Migrations é a única autoridade de evolução do schema; versionar migration e snapshot. Aplicar explicitamente em banco vazio antes de iniciar API/testes. Não combinar EnsureCreated com migrations nem aplicar alterações automáticas no startup da aplicação.
- Tabela `exercises`: `id uuid` primário gerado pela API e `name text not null`. Check de banco impede texto vazio/somente espaços; expressão deve ser coerente com a validação .NET para espaços em branco, com casos de teste de espaço, tabulação e quebra de linha. Nome é texto, não HTML. Sem owner fictício, usuários simulados ou dados importados.
- Nome é aparado nas extremidades, preservando acentos, caixa e espaços internos. Sem unicidade pelo nome, pois identidade/aliases/visibilidade ainda estão abertos. São propostas explícitas para a prova I0, não regras de catálogo aprovadas.
- Não acrescentar limite de caracteres de produto arbitrário neste planejamento. Antes da execução, aceitar o contrato com texto sem limite específico de campo neste I0 ou decidir um limite com mensagem correspondente; limites de transporte são configuração técnica distinta.

### Execução local e isolamento

Escolha confirmada pelo fundador (D69): PostgreSQL em Docker Compose para I0 local. A alternativa de instalação nativa foi considerada e não escolhida. Vantagem: versão do banco e preparação reproduzíveis. Custo: Docker/virtualização e recursos no Windows, cuja disponibilidade não foi verificada. Volume persistente de desenvolvimento e web/API no host continuam como desenho recomendado; a confirmação não aprova automaticamente todo o ADR. Não instalar ou configurar nada nesta etapa.

Testes usam PostgreSQL da mesma versão do desenvolvimento, em instância/volume descartável separados. Recomendação inicial: perfil Compose de testes, bancos de integração e E2E distintos, portas/conexões próprias e execução serial por suíte. Testcontainers é alternativa para lifecycle automático e paralelismo; acrescenta dependência de Docker e orquestração .NET/Node para este recorte. Não usar SQLite ou EF InMemory como prova do PostgreSQL.

Fixtures só podem limpar bancos descartáveis criados pela própria execução, com identificação explícita e conexão validada. Nunca resetar banco de desenvolvimento ou aceitar conexão arbitrária para limpeza. Processos e conexões de teste são distintos dos de uso manual. Migrações são aplicadas também no banco E2E.

Segredos locais da API por configuração fora do Git (por exemplo user-secrets ou variável de ambiente), exemplos sem credenciais reais. Somente URL pública da API vai à configuração do navegador. Compose futuro não deve versionar senhas reais. Dados exclusivamente sintéticos, sem acesso remoto no I0.

### Versões e reprodutibilidade

Escolher versões estáveis suportadas e compatíveis na preparação da execução, verificando documentação oficial e ferramentas disponíveis antes de instalar. Fixar SDK .NET em global.json, versões compatíveis de EF Core/Npgsql, Node LTS em arquivo de versão, dependências exatas por lockfile, ferramenta EF local e imagem PostgreSQL com versão fixada. Não assumir que o mínimo aceito pelo Next.js é a melhor versão do Node. Não houve inventário de ferramentas ou validação de compatibilidade neste planejamento; números exatos continuam pendentes, sem autorizar setup.

### Qualidade proporcional

Divisão confirmada pelo fundador (D72): xUnit com PostgreSQL real para cadastro/listagem/validação/persistência, Playwright para fluxo pela tela/recarga/erros e unitários somente diante de regra própria relevante. WebApplicationFactory, lifecycle/isolamento dos bancos e orquestração abaixo são detalhes técnicos recomendados; não representam configuração já executada.

- xUnit + WebApplicationFactory testa HTTP/validação/persistência com PostgreSQL real, incluindo migração a partir de banco vazio.
- Playwright usa processos web/API reais e Chromium para fluxo de criar/recarregar/listar. WebApplicationFactory usa TestServer em memória e não substitui o servidor HTTP real exigido pelo navegador.
- Funcional de falha pode abortar a requisição no navegador para cenário determinístico; esse teste verifica feedback, não persistência. Caso de falha de banco na integração usa banco de teste indisponível para verificar ausência de 2xx e resposta sem detalhes internos.
- Sem suíte unitária artificial: a pequena validação fica coberta no HTTP. Se a normalização virar regra independente e reutilizada, acrescentar testes unitários focados em seus casos relevantes.
- Build web/API, lint e checagem TypeScript, integração e E2E terão comandos reproduzíveis e reaproveitáveis no pipeline. Sem porcentagem de cobertura arbitrária ou múltiplos navegadores agora.

## Consequências e limites

A escolha reduz camadas e mantém o caminho real de dados, mas acopla persistência ao projeto da API. Extrair módulos/projetos quando regras e dependências justificarem. Ausência de autenticação e ownership limita I0 a prova local sintética; não é catálogo global aprovado. Não migrar esses registros sintéticos para o piloto como se tivessem dono definido.

Retry automático de POST e unicidade por nome não resolvem idempotência. Em perda da resposta após commit, o resultado é incerto: orientar consultar a lista antes de tentar de novo. Idempotency key fica para decisão posterior se o uso exigir garantia de repetição sem duplicação.

Homologação, identidade/RLS, Supabase, offline e mobile não bloqueiam a prova local e não são configurados aqui. Antes de publicar, decidir proteção de acesso e se teste/homologação são um único destino; não criar dois ambientes por nomenclatura.
